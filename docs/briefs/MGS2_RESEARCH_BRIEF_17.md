# MGS2 / RG353VS — результат v2 DirectSound recorder

Этот бриф фиксирует единственный контролируемый прогон v2 из brief #16.
DirectMusic, PipeWire, ALSA, графика и пользовательские настройки в нём не
менялись.

## Что именно было проверено

После перезагрузки устройства игра была запущена заново, пользователь дошёл
до gameplay, затем на устройстве был создан `/tmp/mgs2-sfx-arm`. Пользователь
сделал **два удара**. В этот момент v2 recorder был выбран через launch script
и записал новый файл:

```text
/tmp/mgs2-sfxevents/events-001.log
SHA-256 21247bb3915b2e095454047d62657574006b0b13b04f0066d568fd3ccf856f5f
```

Записанная диагностическая DLL на устройстве имела ожидаемую сумму:

```text
dsound_sfxevents2.dll
SHA-256 6b0a32f66293ac0e62bc3df87ba9b2502b6c4f989504f531ffddc79791bc1c65
```

Сам файл сохранён в репозитории как
`logs/rg353vs/sfxevents/two-punch-v2/events-001.log`.

## Наблюдаемый результат

```text
MGS2_SFX_EVENTS v1 capture=1 start_tick=363345 events=0 overflow=0
```

Строка `v1` — не версия установленной DLL: это не обновлённая строка заголовка
в общем writer-коде. Появление zero-event файла возможно только благодаря
финализатору v2, добавленному после первой попытки.

За окно с двумя ударами **не вошёл ни один** из следующих методов на буфере,
прошедшем точный фильтр recorder:

```text
Lock, Unlock, GetCurrentPosition, SetCurrentPosition,
SetVolume, SetPan, SetFrequency, Play, Stop,
GetStatus, AcquireResources
```

Фильтр был намеренно очень узким:

```text
bytes=32576, 44100 Hz, mono PCM16, DSBCAPS_LOCDEFER
```

## Что это доказывает — и чего не доказывает

Это исключает предположение, что два удара запускают effect через один из
перехваченных методов **именно этого** 32 576-байтного буфера. Поэтому
исправлять `SetCurrentPosition`, `Play`, `Lock/Unlock` или LOCDEFER на основе
этого буфера сейчас нельзя: подтверждающей последовательности нет.

Это **не** доказывает, что MGS2 не использует DirectSound совсем. Остаются
ровно три правдоподобные ветви:

1. Игра меняет этот persistent buffer через ранее сохранённый указатель на
   память, не вызывая COM-методы после удара.
2. Эффект обслуживает другой secondary buffer, не совпадающий с выбранными
   размером/форматом/caps.
3. Игровые SFX проходят через иной audio API/внутренний путь, тогда как
   наблюдавшийся 32-КБ пул относится к другому аудиоканалу.

## Единственная обоснованная следующая диагностика

Если продолжать измерение, следующий recorder не должен снова угадывать один
буфер по размеру. Нужен компактный **inventory recorder** только для
DirectSound:

* при `CreateSoundBuffer` присвоить каждому secondary buffer ID и записать
  descriptor (bytes, format, caps, flags);
* после marker записывать 2–3 секунды вызовы уже для всех созданных secondary
  buffers, с ID из inventory;
* оставить кольцевой лимит и не читать PCM/не менять mixer, чтобы тест не
  вносил прежние фризы;
* сопоставить любой активный ID с его descriptor, а затем переносить только
  подтверждённый семантический патч.

Это один следующий игровой прогон, который различит все три ветви. До него
нет конкретного, проверяемого аудио-фикса; любые изменения текущего `dsound`
были бы возвратом к уже отвергнутому угадыванию.

## Состояние после замера

Диагностический launcher снят сразу после копирования файла. На устройстве
восстановлен сохранённый штатный `launch.sh`:

```text
SHA-256 f36bd9f09cd2f690da2424ca77746cf2fbb06dc154ddf8f1a49e3786e253bff1
```

То есть следующий обычный запуск снова использует штатный DirectSound и не
несёт recorder-поллинг или запись лога.
