# MGS2 first-use shader stalls: exact-source deduplication (2026-08-13)

## Result

Patch 32 is production. WineD3D's fixed-function shader caches distinguished
several D3D settings keys that generated byte-identical GLSL. Each alias became
a new GL shader and, with patch 27, a new separable stage program. On the
corrected save-load/enemy route the control built 36 stages from only 19 unique
sources. The 17 redundant stage links cost 2,036,500 us.

Patch 32 keeps the existing settings caches but shares their GL shader and stage
program owner when the generated source is exactly equal. The cache-on capture
contains no duplicate compile or stage-link event. The stripped production DLL
is deployed and byte-verified:

```text
fb1554e0dd01f276192a23810ed60e9c4be0c6ab1703825caceaacf04161c17d
    wined3d_p32_ffp_source_dedup.dll
```

This removes redundant first-use stalls. It does not remove the first link of a
genuinely new shader, so it is not evidence that every map or enemy transition
is now hitch-free.

## The route had been testing a wall

`harness/autoload_save.py` used twelve `up` walking bursts. The loaded save puts
Raiden against the upper closed door, so every burst walked into the wall. The
per-step screenshots proved that the route never reached the guard it was meant
to exercise.

The default is now `down`, with `MGS2_WALK_KEY` retained as an override. A manual
2.5 s `down` hold exposed the guard and immediately added six stage links costing
1,616.9 ms; the driver reported a separate 979 ms gameplay frame. This directly
connects the reported "new enemy" hitch to first-use shader work.

## What the source capture measured

The existing bounded `MGS2_GPU_PROBE` ring was extended so `compile_shader`
records carry a 64-bit FNV-1a source hash and byte length. It still performs no
I/O from the render thread. The diagnostic capture before the fix recorded:

```text
39 compile_shader events
39 link_separable_stage events, 6,106,276 us total
19 byte-distinct GLSL sources
20 redundant links, 2,363,799 us total
    4 vertex duplicates,   878,702 us
   16 fragment duplicates, 1,485,097 us
```

That run used the diagnostic launcher with Box86 SAFEFLAGS=0, so its timing is
not a production comparison. Source equality and event counts are still valid.

## Device A/B

The decisive A/B used the same newly built DLL, corrected route, one walking
burst, one process and `BOX86_DYNAREC_SAFEFLAGS=1`. The only change was
`MGS2_GL_SOURCE_DEDUP`:

```text
                                      cache off       cache on
compile_shader / stage-link events       36              22
unique source hashes                     19              22
duplicate source hashes                  17               0
total stage-link time                 5,770,460 us     4,555,622 us
longest stage link                       320,737 us       320,605 us
post-load image incl. first guard        correct          correct
```

The animation/timing-dependent route reached three additional unique sources in
the cache-on run, so subtracting the two total times is not a controlled estimate
of the full gain. The controlled claim is stronger and narrower: all 17 aliases
in the off arm were exact source duplicates, cost 2,036,500 us, and none was
compiled or linked in the on arm.

The three worst frames printed by the wrapper remained similar:

```text
cache off       5777 / 3509 / 2986 ms
cache on        5660 / 3471 / 3024 ms
production DLL  5618 / 3469 / 2984 ms
```

Those maxima are dominated by save loading and unique first-use work. Patch 32
instead removes the repeated 90--220 ms links within the sequence. Do not claim
that it solved the whole multi-second load from those maxima.

## Why sharing is safe

The hash is only a rejection filter. A hit also requires equal length and a full
`memcmp`, so a collision cannot merge different GLSL.

The D3D settings descriptors remain separate. Only the generated GL shader,
separable stage program and its uniform-location table are shared. Exact GLSL
has the same declared uniforms and inputs, and the constant-update mask is
derived from those locations. A common owner survives both descriptor trees;
pipelines/programs are deleted first, then the stage program and shader are
deleted once. This avoids both double deletion and a driver-side use-after-free
during save-load teardown.

`MGS2_GL_SOURCE_DEDUP=0` is the one-run rollback/A-B switch.

## Hypotheses closed in this run

### "An older performance patch causes the loading stalls"

Not supported. The earlier whole-stack A/B already made the least-optimised
renderer worse (8,679 ms longest stall against 6,591 ms for the full stack).
The direct capture here instead found avoidable duplicate work inside the normal
first-use shader path. Patch 31 remains off for its separate playability problem;
patches 27--29 stay enabled.

### Mali shader LTO or pilot shaders

Both were tested through files named by `MALI_DEBUG_CONFIG`; the driver confirmed
that it parsed one variable in each arm. Neither materially changed stage-link
cost:

```text
default                 40 stages, 6,180.1 ms, 154.5 ms avg, 320.1 ms max
GLES_DISABLE_SHADER_LTO 41 stages, 6,234.5 ms, 152.1 ms avg, 312.7 ms max
disable pilot shaders   40 stages, 6,106.4 ms, 152.7 ms avg, 320.5 ms max
```

The differing stage count prevents a precise total-time comparison, but neither
candidate moved per-stage cost enough to justify a production driver knob.

### Storage paging

The warm-I/O load still produced a 5,834 ms frame with only four major faults.
Paging is not the cause of the captured shader-link stalls.

## Next bounded work

The remaining target for **first-use hitches** is the first link of genuinely
new sources, especially the 200--320 ms vertex stages and unique work inside the
multi-second load. Do not retry persistent program binaries: this driver rejected
its own exported binaries across processes, and linking identical source twice
cost the same. A future candidate needs to move known exact FFP stages earlier
within the same GL context (for example a measured, bounded prewarm set), then
be judged on a real transition/enemy route rather than average corridor fps.

This is not a claim about sustained reinforcements combat throughput. The valid
14 August profile found 11.9--19.5 fps with `wined3d_cs` roughly half in Box86
Wine and half already-native Mali driver code; its next question is remaining
driver submissions, documented separately in
`MGS2_REINFORCEMENT_ARM_TARGET_2026-08-14.md`.
