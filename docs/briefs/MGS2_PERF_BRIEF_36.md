# MGS2 RG353VS — бриф #36: лестница пройдена, кадр разложен по слоям

Дата: 7 августа 2026. Первый полный замер декомпозиции рендерера на production.
Отвечает на вопрос, который стоял открытым с #29: **где именно находятся те
60 миллисекунд, которые нужны для 24 fps**.

Всё измерено на устройстве, тяжёлый открытый Plant, сейв `Game Data 02`,
фиксированный спот, владелец стоял неподвижно.

## Ответ

Числа ниже — **только окна с фактическим потолком 1416000**. Первая редакция брифа
считала средние по всем окнам, включая те, где ядро сбросило потолок до 1104 и 816,
и из-за этого занижала producer и завышала floor. Исправлено.

```text
53.70 мс   применение состояния на consumer + GL + драйвер     (0 − C)
 1.43 мс   обход ресурсов                                       (R − 0)   БЕСПЛАТНО
-0.28 мс   аллокация пакета CSMT + publish + consume            (C − B)   БЕСПЛАТНО
15.55 мс   producer-подготовка d3d8, включая apply_stateblock    (B − A)
34.60 мс   игровая логика + Box86 + аудио + цикл сообщений       (A)
---------
68.97 мс   ВЕСЬ путь D3D (0 − A)
103.57 мс  базовая
```

Средние по чистым окнам: `0 = 103.57`, `A = 34.60`, `B = 50.15`, `C = 49.87`,
`R = 105.00`.

**Частотная проверка ступени A, которая придаёт ей вес.** Окно A при 1104 МГц дало
44.6 мс. Пересчёт `44.6 × 1104 / 1416 = 34.77 мс` против измеренных при 1416
**34.60 мс** — совпадение почти идеальное. Значит этот floor действительно почти
чисто ограничен частотой CPU, а не чем-то ещё.

## Семантика ступеней, установленная по исходнику

Не по названиям, а по коду — это оказалось важно, см. раздел про ошибки.

```text
0   базовая, ничего не отключено
A   d3d8 Draw* выходит ДО mutex, managed-текстур, sysmem-upload,
    set_primitive_type и apply_stateblock -> работы D3D8 нет вообще
B   всё это выполняется, включая apply_stateblock, но
    wined3d_device_context_draw не вызывается -> нет emit_draw, нет обхода
    ресурсов, нет CS-пакета
R   emit_draw выполняется и публикует пакет, пропускается только
    reference_graphics_pipeline_resources
C   пакет создан, опубликован и получен consumer'ом, а draw_primitive выходит
    сразу -> нет применения состояния и нет GL
```

Ступень R добавлена специально для этого прогона: без неё B убирает обход ресурсов
и пакет одновременно, и разделить их нечем.

Все ступени кроме 0 — диагностические. R вдобавок небезопасна по построению:
consumer может работать с ресурсами, время жизни которых больше не удерживается.
Пригодна для окна в 30 секунд, но не как настройка.

## Что закрыто

Три направления из плана оптимизации отпадают сразу, и это главная экономия:

```text
обход ресурсов / access_time stamps       R − 0 = +1.4 мс -> нечего оптимизировать
    значит active masks, специализированный reference_..._d3d8 и deferred
    last-use stamping не нужны
аллокация и публикация пакетов CSMT       C − B = -0.3 мс -> нечего оптимизировать
    значит packet coalescing и сокращение числа публикаций в очередь не нужны
ОПТИМИЗАЦИЯ producer-механики             publish бесплатен, оптимизировать нечего
```

**Важное уточнение, которого в первой редакции не было.** Закрыта *оптимизация*
механики producer, но не **агрегация** на нём. Publish действительно бесплатен, а
вот десять обычных draw'ов это десять producer-подготовок плюс десять применений
состояния плюс десять glDraw. Один батч — это одна подготовка, одно применение
состояния и один multi-draw, то есть агрегация у producer атакует сразу все
измеренные 69 мс. Producer остаётся лучшим местом для объединения, просто не для
микрооптимизации.

Ожидание было обратным: атомики `InterlockedExchange` под Box86 на Cortex-A55 и
повторные штампы `access_time` выглядели дорогими. Измерение это не подтвердило.

## Предел, и ИСПРАВЛЕНИЕ первой редакции

Первая редакция утверждала: «даже идеальное удаление рендерера не даёт 24 fps».
**Это верно только для ступени C и вводило в заблуждение.** Различать надо две
разные вещи:

```text
удаление consumer-рендерера (C)   -> 49.87 мс = 20.1 fps   ниже минимума
удаление ВСЕГО пути D3D     (A)   -> 34.60 мс = 28.9 fps   ВЫШЕ минимума 24
```

То есть 24 fps математически достижимы даже при 1416 МГц, если атаковать **весь**
путь D3D, а не только его consumer-половину.

```text
бюджет 24 fps                41.67 мс
floor игры при 1416          34.60 мс
остаётся на весь D3D          7.07 мс
измеренный путь D3D          68.97 мс
--------------------------------------
требуемый batch factor        9.8x
```

А частота требования резко снижает, потому что floor масштабируется с ней почти
линейно (проверено выше):

```text
частота   floor      путь D3D   место под D3D   нужный batch factor
1416      34.60 мс   68.97 мс    7.07 мс        9.8x
1608      30.47      60.73      11.20           5.4x
1800      27.22      54.25      14.45           3.8x
1992      24.60      49.02      17.07           2.9x
```

Оговорка: строки для 1608-1992 предполагают, что путь D3D масштабируется с частотой
так же, как floor. Для CPU-части это правдоподобно, для драйверной — не обязательно.
Ступень D как раз отделит одно от другого. **Это модель, не прогноз fps.**

Практический вывод: при устойчивых ~2 ГГц достаточно batch factor ~2.9x, то есть
средних естественных серий по 3 draw'а. Это уже не фантастика — и именно поэтому
физический теплоотвод и батчинг вместе стоят больше, чем каждый по отдельности.

## Моя ошибка в этом прогоне

В первом прогоне смонтирован `d3d8_mgs2fast1.dll`, в котором ступеней A и B **нет
вообще** (`MGS2_D3D8_NOOP_DRAW=0`, `MGS2_D3D8_NOOP_SUBMIT=0`) — они живут в
`d3d8_ladder1.dll`. Поэтому пять окон A и B в первом прогоне это базовая ступень.
Обнаружено по тому, что A оказалась медленнее C, чего быть не может: A убирает
надмножество работы C. Потребовался второй прогон и второй забег владельца на спот.

Урок в копилку к правилу #4: сверять `cmp`/`sha256` **и** наличие самих ручек в
модуле, а не только имя файла. Манифест раннера теперь печатает хеши обоих
модулей до первого числа именно поэтому.

# Собрано для следующего прогона: `wined3d_ladder3.dll`

Один билд, четыре вещи, никаких новых трассировок:

```text
ступень D          вернуться непосредственно перед реальным glDraw*, после ВСЕГО
                   применения состояния. MGS2_RUNG_D=1 или буква D в файле ступени
                   D - C = context/state/resource setup + GL state calls
                   0 - D = сам glDraw* + submission драйвера Mali
census серий       MGS2_DRAW_CENSUS=1, только счётчики, строка в секунду, канал
                   mgs2stat. Считает подряд идущие совместимые WINED3D_CS_OP_DRAW:
                   гистограмма серий 1/2/3-4/5-8/9-16/17+, draws в сериях >=2 и >=4,
                   максимальная серия, число батчей и effective factor,
                   плюс причины разрыва: prim, indexed, base vertex, state, vb, ib
multi-draw probe   одноразовая строка MGS2MULTIDRAW: advertised/absent для
                   GL_EXT_multi_draw_arrays и GL_OES_draw_elements_base_vertex
ступени A и B      те же, для повторного замера при одной устойчивой частоте
```

Обратной ступени «glDraw без применения состояния» намеренно нет: она оставила бы
GL-состояние несогласованным и дала бы бессмысленное число.

Оговорка по multi-draw probe: из wined3d на этой стадии нельзя взять адрес функции
(`p_wglGetProcAddress` в `gl_ops` отсутствует, а этих имён нет в его таблицах).
Поэтому проверяется **строка расширений** — это первичный фильтр: если расширение
не объявлено, оно непригодно независимо от указателя. Прошлая проверка по экспортам
ELF была недостаточной именно потому, что точки входа GLES не обязаны быть
экспортированными символами.

Прогон, который нужен, короткий — не пятнадцать окон:

```text
RUNGS="C D 0 D C  0 D C D 0"     10 окон x 30 с = 5 минут
плюс отдельно MGS2_DRAW_CENSUS=1 на 20-30 секунд, БЕЗ смешивания с лестницей:
    fps телеметрии нельзя использовать как benchmark, пока она не доказана бесплатной
```

И для честной частоты в новом прогоне стоит снимать не только заявленный потолок, а
`time_in_state` до и после каждого окна — единичный `scaling_cur_freq` уже один раз
ввёл в заблуждение.
