# MGS2 RG353VS — бриф #38: настоящая батчируемость, механизм и сам батчер

Дата: 8 августа 2026. Продолжение #37. Здесь закрыты оба дефекта census из #37,
проверен механизм склейки на живом драйвере и написан батчер. Он **собран, но ещё
не измерен на устройстве** — это единственное, что осталось.

Всё, что помечено как измеренное, снято на устройстве: тяжёлый открытый Plant,
`Game Data 02`, фиксированный спот, владелец стоял неподвижно,
`MGS2_FREQ_STEPS="1416000"`.

---

## 1. Дефект census №1 закрыт: настоящий factor 8.49x, не 10.11x

В #37 поле `state_since_draw` было объявлено, но нигде не инкрементировалось,
поэтому `state=0` не значило «состояние не менялось», и 10.11x был **верхней
границей**, а не результатом.

Инкремент нельзя было поставить в обработчик state-пакета: пакеты кладутся в
очередь producer'ом, а исполняются consumer'ом, и «между двумя draw'ами» — понятие
очереди, а не исполнения. Барьер поставлен там, где пакет **публикуется**:

```c
static unsigned int mgs2_submitting_draw;
static unsigned int mgs2_census_epoch;

static inline void wined3d_device_context_submit(...)
{
    if (!mgs2_submitting_draw) ++mgs2_census_epoch;   /* любой НЕ-draw пакет */
    context->ops->submit(context, queue_id);
}
```

Серия рвётся при смене epoch. Это консервативно в нужную сторону: любой пакет,
который не draw — смена состояния, clear, blit, обновление subresource, query —
считается разрывом, даже если он на самом деле безобиден.

**Пересъёмка на том же споте, тот же клок:**

```text
                      #37 (сломанный)   #38 (консервативный)
draws/с                   13091              12014
batches/с                  1295               1415
factor                    10.11x              8.49x
```

Настоящая цифра оказалась **8.49x**, а не «сильно ниже 10x», как я предполагал.
Требование из #37 при 1416 МГц — 9.7x, при 1992 МГц — 2.8x. То есть
батчируемости хватает с большим запасом.

**Форма серий:**

```text
подряд идущих (contiguous)   90.7%
все примитивы                99.8% TRIANGLESTRIP
разрывы: смена vertex buffer  97%
         смена типа примитива  ~3%
         index buffer / base vertex / state   0
```

## 2. Дефект census №2 закрыт: indexed=0 — это ФАКТ, а не ошибка чтения

В #37 я записал `indexed=0` в дефекты: игра ведь вызывает
`DrawIndexedPrimitive`. Проверено по исходнику пути d3d8 → wined3d: в этой сцене
игра выдаёт **только** non-indexed `DrawPrimitive`.

```text
idx=0   nonidx=13057
```

Флаг читался верно. Дефекта не было. Это важно не как бухгалтерия, а потому что
именно на этом факте держится безопасность выбранного механизма — см. §4.

## 3. Механизм проверен на живом Mali

multi-draw закрыт в #37 (`GL_EXT_multi_draw_arrays` absent на живом контексте).
Остаётся склейка нескольких strip'ов в один `glDrawElements` с
`GL_PRIMITIVE_RESTART_FIXED_INDEX` между ними.

Склеить non-indexed strip'ы напрямую нельзя: один `glDrawArrays` на объединённый
диапазон сварит их вместе и **придумает треугольники** на стыках.

Перед тем как писать батчер, механизм проверен на одном strip'е
(`MGS2_STRIP_AS_INDEXED=1`): взять один non-indexed strip и выдать его как
indexed через scratch element buffer.

```text
MGS2STRIP: strip as indexed: count=4 start=0 16bit | drained 1 stale errors |
           glEnable(PRIMITIVE_RESTART_FIXED_INDEX) err=0x0 OK
           glDrawElements                          err=0x0 OK
```

Три вещи, которые пришлось выяснить, и каждая формирует код:

```text
d3d8 передаёт WINED3D_NO_PRIMITIVE_RESTART (d3d8/directx.c:478) -- и правильно:
    0xFFFF -- легальный индекс в D3D8. Значит restart включается локально, только
    вокруг склеенного draw'а
ARB_ES3_COMPATIBILITY промотируется только при GL 4.3 (adapter_gl.c:3413), а
    контекст сообщает 3.2 -> wined3d считает restart недоступным. На настоящем
    GLES 3.x токен core с версии 3.0, что и подтвердилось
GLES 3 запрещает client-side index arrays -> нужен настоящий buffer object
```

### Ловушка: первое чтение дало err=0x500

`GL_INVALID_ENUM` был **устаревшей** ошибкой из очереди: при `WINEDEBUG=-all`
никто не вызывает `glGetError`, и очередь копится с самого старта. Исправление —
сначала осушить очередь, потом проверять каждый вызов отдельно. После этого
OK/OK. Это общее правило для всего проекта: **любая проверка `glGetError` в этом
порте обязана сначала осушить очередь**, иначе она читает чужую ошибку.

## 4. Батчер: где он живёт и почему именно там

`dlls/wined3d/context_gl.c`, флаг `MGS2_BATCH=1`, по умолчанию выключен.
`MGS2_BATCH_MAX` ограничивает серию, по умолчанию 256, максимум 512.

Накопитель — массивы `first[]`/`count[]`, режим, максимальный индекс. Draw
поглощается вместо выдачи:

```c
if (!idx_size)
{
    if (mgs2_batch_enabled() && mode == GL_TRIANGLE_STRIP
            && mgs2_batch_append(context_gl, mode, start_idx, count))
        return;
    ...
}
```

`mgs2_batch_flush()` собирает индексы `first..first+count-1` через один разделитель
между кусками, кладёт их в постоянный BO (`glBufferData` при росте, иначе
`glBufferSubData`) и выдаёт один `glDrawElements` с restart, включённым только
вокруг него.

**Четыре точки сброса, и почему каждая обязательна:**

```text
1  любой НЕ-draw пакет CSMT              cs.c: mgs2_cs_dispatch()
2  грязное graphics state перед draw'ом   context_gl.c: в draw_primitive,
                                          ДО context_apply_draw_state
3  present                                cs.c: wined3d_cs_exec_present, первым делом
4  серия достигла MGS2_BATCH_MAX          context_gl.c: mgs2_batch_append
```

Точка 1 — тот же барьер, которым мерил census, вынесенный в исполнение:

```c
static inline void mgs2_cs_dispatch(struct wined3d_cs *cs, enum wined3d_cs_op opcode,
        const void *data)
{
    if (opcode != WINED3D_CS_OP_DRAW)
        mgs2_batch_flush();
    wined3d_cs_op_handlers[opcode](cs, data);
}
```

Вставлен во **все три** цикла обработки опкодов (`wined3d_cs_st_submit` и два пути
mt-worker'а) — пропустить один значит склеить через смену состояния в одном из
режимов.

Точка 2 стоит **до** `context_apply_draw_state`: после этой строки GL уже не держит
то состояние, под которым были выданы отложенные draw'ы. Проверка — обход
`context->dirty_graphics_states` (битмап, `wined3d_private.h:1867`). Indexed или
instanced draw тоже завершает серию: склейка умеет только non-indexed strip'ы.

Точка 3 — единственная неотменяемая: серия, оставшаяся в конце кадра, была бы
нарисована в **следующем**, а readback её бы не увидел.

**Соображение, которое пришлось проверить, а не предположить:** сбросы в точках 1 и
3 происходят вне скобок `context_acquire`/`context_release`. Годится ли это?
`wined3d_context_gl_release` (context_gl.c:1587) только уменьшает `level` и, если
был сохранён внешний контекст, восстанавливает его — **EGL-контекст с потока не
снимается**. Оба сброса выполняются на том же потоке CSMT, который сделал контекст
текущим, поэтому GL-вызовы попадают куда надо. Если контекста никогда не было,
`flush` выходит сразу по `!mgs2_batch.n || !context_gl`.

**Границы безопасности restart-индекса:**

```text
16-битные индексы, пока max_index < 0xFFFF, иначе 32-битные (restart 0xFFFFFFFF)
0xFFFF безопасен как разделитель ТОЛЬКО потому, что census доказал: в этой сцене
    игра не выдаёт indexed draw'ов вообще (§2), поэтому столкнуться с настоящим
    индексом он не может
серия из одного draw'а выдаётся обычным glDrawArrays -- индексный буфер не стоит
    того
```

Если в игре появится indexed draw — серия сбрасывается, и он идёт обычным путём.
Но если indexed draw'ы станут в этой сцене нормой, §4 надо пересматривать заново.

Счётчики (`draws=`, `batches=`, `factor=`, размер индексов, разбивка сбросов по
четырём причинам) печатаются **одной строкой в секунду**, никогда на draw — правило
2 из AGENTS.md.

## 5. Сборка: ловушка сработала снова, и её надо записать явно

`MGS2_RELEASE` — это не отдельная реализация `draw_primitive`, а блок `#define`,
превращающий тридцать `mgs_*` хелперов в константы. Он есть **только** в
`context_gl.c`. Значит любая пересборка `context_gl.o` без этого определения
возвращает ~30 лишних вызовов на draw, то есть ~315 000 в секунду под Box86, и
делает измерение бессмысленным.

Флаг **нельзя** передать через `CFLAGS=` или `EXTRACFLAGS=`: правила PE-сборки в
сгенерированном Makefile содержат флаги буквально. Рабочий способ ровно один:

```bash
make dlls/wined3d/i386-windows/wined3d.dll i386_CC="i686-w64-mingw32-gcc -DMGS2_RELEASE"
```

Первая попытка через `CFLAGS=` прошла без ошибок и дала diagnostic-сборку молча.

**Проверка по строкам DLL тоже обманывает.** `strings | grep MGS2_FACESAMPLEQUERY`
находится и в release-сборке, потому что `#define` убирает *вызовы*, а определения
функций со своими строками остаются. Валидная проверка — сравнение с известной
release-сборкой:

```text
MGS2_FACESAMPLEQUERY   wined3d_release3.dll = 0   новая сборка = 0   OK
MGS2_SKIP_ALL_DRAWS    wined3d_release3.dll = 0   новая сборка = 0   OK
MGS2_BATCH                                        новая сборка = 1   батчер внутри
```

## 7. Что измерить, и что считать опровержением

Один прогон, фиксированный спот, `MGS2_FREQ_STEPS="1416000"`, база 102.4 мс:

```text
MGS2_BATCH=0   должен совпасть с production в пределах разброса 3.2 мс
               -- иначе баг в коде, который не выключается флагом
MGS2_BATCH=1   ожидание из модели: 52.75 мс пути draw'ов делится примерно на
               8.49 -> кадр ~62 мс -> ~16 fps. До 24 fps при 1416 МГц не хватает,
               и это ожидаемо: #37 требует 9.7x при этой частоте
```

Судить **и по картинке тоже**. Склейка через restart — единственное место в этом
патче, которое может нарисовать неправильную геометрию, и проявится это как
треугольники-стяжки между объектами, а не как падение fps.

Что опровергает подход:

```text
factor в строке MGS2BATCH сильно ниже 8.49 -> барьеры сбрасывают чаще, чем
    считал census; смотреть разбивку flush dirty/incompat/present/full
factor ~8.5, а кадр не изменился -> цена не в числе вызовов, а в объёме работы
    драйвера на вершину, и тогда рендерер как направление закрыт
геометрия ломается -> либо restart не работает так на этом Mali несмотря на
    err=0, либо сбрасывать надо в ещё одной точке
```
