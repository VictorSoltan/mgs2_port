# MGS2 RG353VS — бриф #29: передача работы по оптимизации

Дата: 7 августа 2026. Это самодостаточный бриф для человека, который займётся
**только производительностью**. Всё, что нужно знать, здесь; предыдущие 28 брифов
нужны лишь как первоисточник, читать их целиком не обязательно.

Главное правило чтения: числа в этом брифе — измеренные на устройстве. Там, где
что-то предполагается, это сказано явно. Список тупиков в конце важнее списка
идей: половина из них выглядит очевидно правильной, пока не измеришь.

## Задача и критерий приёмки

Игра запускается, звук работает, сейвы работают. Нужен комфортный кадр.

```text
цель            стабильные 30 fps в открытых локациях
минимум         устойчивые 24 fps
frame pacing    p95 не хуже 42 мс
фризы           кадров дольше 200 мс нет
```

Сейчас: 22-38 fps стоя в помещении, 60 на лёгких экранах, **6.5-17 fps в
открытом Plant**, плюс отдельные остановки на секунды.

## Стек. Не переоткрывать, он зафиксирован

```text
Anbernic RG353VS: Rockchip RK3566, 4x Cortex-A55 до 1992 МГц (разогнан),
                  Mali-G52, 999 МБ ОЗУ, ROCKNIX, sway (wlroots) на Wayland
игра              MGS2 Substance, 2003, 32-битный PE, Direct3D 8, 640x480,
                  InternalResolution=512, все настройки графики уже в минимуме
цепочка           MGS2 -> d3d8 (builtin Wine) -> WineD3D с CSMT -> GLES
                  -> EGL pbuffer -> glReadPixels -> wl_shm -> sway
эмуляция          Box86 0.3.9 исполняет весь x86-код: и игру, и PE-часть Wine
GPU userspace     штатный блоб libmali-bifrost-g52-g29p1, только GLES, без desktop GL
```

Обязательные условия: `CSMT=1` (с `csmt=0` игра не стартует), разрешение не
снижать (решение владельца), звуковую конфигурацию не трогать.

## Куда уходит кадр. Канонические числа

Открытая локация Plant, замерено тремя каналами одновременно:

```text
draw calls              ~10 500 в секунду, то есть ~1000 на кадр
                        (для сравнения: лёгкий экран при 60 fps — ~190 на кадр)
кадр при 9.5 fps        105 мс, из них GPU 1.5 мс (после перекрытия), CPU ~103 мс
ожидание GPU            2.8 мс в коридоре, до 31.7 мс с видом на весь Plant
перенос кадра 640x480   0.75 мс (~1.6 ГБ/с, нормально)
wined3d_cs              49-68% одного ядра
потоки игры             108-117% одного ядра
микшер DirectSound      15-18% ядра (цена рабочего SE, трогать нельзя)
занято всего            51-53% четырёхъядерной машины, два ядра простаивают
ожидание компоновщика   0.00 мс
память                  280 МБ свободно, свопа нет, major faults ~900 за сессию
```

**Вывод, на котором стоит всё остальное: кадр упирается в CPU.** Не в память, не
в пропускную способность, не в компоновщик, и после перекрытия — не в GPU.

## Тепловой бюджет. Самый крупный неиспользованный резерв

```text
потолок частоты за сессии гулял: 1992, 1800, 1608, 1416, 1104, 816 МГц
на зарядке устойчиво сидит на 1104-1416 при 83-85 C
сторож: вниз при 84 C, вверх при 76 C, стоп при 88 C (железо ресетится ~92-95)
```

Механизм самоусиливающийся: тяжёлая сцена греет, сторож режет частоту, сцена
становится тяжелее. Контролируемое сравнение 1608 → 1992 дало **+29% fps**, а
сейчас в игре бывает 1104. **Замер без зарядки до сих пор не сделан** — это
первое, что стоит сделать новому человеку, стоит ноль работы и потенциально
крупнее любого патча.

## Что уже сделано, с измеренным эффектом

| изменение | эффект |
|---|---|
| потолок частоты 1608 → 1992 (плата разогнана до 1992) | **+29% fps**, температура не выросла |
| `d3d8=builtin` вместо сторонней обёртки d3d8→d3d9 | ожидание GPU 7.0-7.7 → 3.8-4.2 мс |
| managed-текстуры грузятся только при изменении | убрано 10 494 из 10 501 сканирований в секунду при нуле реальных загрузок |
| release-сборка wined3d | 30 хуков из `draw_primitive` → 0, TRACE/debug вырезаны, −1.3 МБ |
| убран пропуск чёрного квада в рации | правки CrossOver починили причину, костыль был лишним |
| `PeekMessage` busy-loop (ранее) | **+11% fps**, разброс кадра 12.9% → 5-8% |
| `NtYieldExecution` (ранее) | **+3.4%** |
| тепловой сторож без форков | ~1.5% ядра |

## Открытые направления, по убыванию ожидаемой отдачи

### 1. Тепло. Бесплатно, и потенциально крупнее всего остального

Пройти фиксированный участок Plant **без зарядки**, снять fps и `scaling_max_freq`.
Если потолок держится на 1800-1992 вместо 1104, это плюс 60-80% частоты на
CPU-bound нагрузке. Дальше по этой ветке: андервольт через opp-table, физическое
охлаждение, порог `TEMP_DOWN` 84 → 86 (только после длительной кривой без зарядки).

### 2. Тысяча draw call'ов на кадр. Настоящее узкое место

Это единственное направление, которое бьёт по 103 мс работы CPU. Ни одна из
проверенных идей его не трогала.

Сначала нужен census батчируемости — счётчики в памяти, одна строка в секунду:

```text
полный batch key: indexed/non-indexed, primitive type, VB+offset+stride,
    IB+format, base vertex, FVF, program, textures, samplers,
    blend/depth/cull, render target, world/view/projection, FFP constants
категории: A полностью одинаковый key, B та же геометрия и материал но другая
    world matrix, C уникальные
гистограмма длин серий: 1, 2, 3-4, 5-8, 9-16, 17+
```

Дальше по результату: `GL_EXT_multi_draw_arrays` для серий с одинаковым
состоянием, instancing для случая B, либо точный frustum culling по AABB
диапазонов статических VB — последнее не меняет картинку, в отличие от LOD.

Порог принятия: батчинг имеет смысл, если хотя бы 30% draw'ов входят в серии
длиной от двух.

### 3. Уменьшить реальное время GPU: mediump в FFP-шейдерах

Единственный рычаг по 31.7 мс работы GPU (не по ожиданию, а по самой работе). На
Bifrost FP16 даёт до двойной пропускной способности. `highp` оставить для
`gl_Position`, матриц, глубины; `mediump` для цветов, текстурных координат,
комбинирования, тумана, освещения. Проверять попиксельным сравнением снимков.

Ожидание скромное: GPU это ~20% кадра, так что даже треть его времени это
единицы процентов итогового fps. Но это честные проценты.

### 4. Фризы: ожидание внутри Wine

Измерено снаружи процесса: во время остановки диск читает **ноль**, процессор
простаивает, температура падает, главный поток стоит на `anon_pipe_read` и
`ntsync_schedule`, `wined3d_cs` на `__futex_wait`. То есть это ожидание объекта
синхронизации Wine или обращения к wineserver, а не подгрузка, не шейдеры и не
троттлинг.

Оговорка: наблюдатель читал `wchan` для полусотни потоков 10 раз в секунду, что
разворачивает стек каждого потока в ядре, и почти наверняка усиливал измеряемое.
Длительности из тех захватов не репрезентативны.

Следующий шаг: замер без внешнего наблюдателя (одна строка от презентера на кадр
дольше 500 мс), затем наблюдение только за wineserver — раз в полсекунды, без
`wchan`. Если подтвердится, что игра ждёт wineserver, дальше смотреть ntsync и
частоту серверных вызовов.

### 5. Мелочи после основного

```text
box86 собрать под Cortex-A55 (-mcpu=cortex-a55)     оценка 2-6%
PGO для wined3d/d3d8                                 после функциональных правок
провести glClearDepthf через unix-сторону opengl32   уберёт полноэкранный
    треугольник, которым сейчас чистится глубина; механизм уже готов и проверен
    в opengl32_glesbinary1.so, осталось применить к другой паре функций
```

### 6. Крупная ветка на будущее: Hangover

ARM64 Wine с эмуляцией только приложения. Убирает ABI-стену `wl_egl_window`
(появится нативный zero-copy путь), удешевляет вызовы Wine, снимает барьер с
GLES точками входа. Но это пересборка всего стека и перенос десяти модулей
патчей, и до первого кадра там ничего не измерить. Браться только после того, как
исчерпаны пункты 1-3.

## Методика. Нарушение любого пункта делает замер бессмысленным

- **Сцена решает больше любой настройки.** Внутри одного запуска окна дают 22 и 60
  fps. A/B без фиксированного спота измеряет сцену, а не вариант.
- **Фиксировать частоту.** `MGS2_FREQ_STEPS="1416000"` на оба прогона, иначе
  сравниваются температуры.
- **Не логировать из горячего потока то, что измеряешь.** Цензус микшера в одну
  строку в секунду поднял поток dsound со 169 до 930 тиков и слышался как
  заикание. Внешний наблюдатель с `wchan` усиливал фризы. Оба раза инструмент
  создавал дефект, который потом искали.
- **Проверять смонтированное побайтово.** Лаунчер подменяет DLL через bind-mount;
  сверять `cmp`, не по имени файла.
- **Один экземпляр игры.** Фоновый запуск переживает ssh-сессию, две копии
  читаются как жуткий лаг.
- **Считать не только среднее.** Гистограмма кадров дольше 50/100/200/500 мс уже
  встроена в презентер: среднее по 300 кадрам прячет остановку на 10 секунд.

## Если коротко

Кадр упирается в процессор: тысяча draw call'ов и 103 мс CPU при 1.5 мс GPU.
Всё, что можно было снять с GPU и с презентации, уже снято и это ничего не дало.
Осталось два настоящих рычага — **тепловой бюджет** (бесплатно, до +60-80%
частоты) и **число draw call'ов** (требует census и, возможно, изменения
видимости сцены). Остальное — единицы процентов.
