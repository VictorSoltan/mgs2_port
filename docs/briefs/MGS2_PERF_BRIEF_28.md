Дата: 6 августа 2026. Один прогон владельца в открытой локации Plant, 40 секунд
игры плюс подход к месту. Заставку в этот прогон снять не удалось.

Все числа ниже сняты одновременно тремя каналами (презентер, wined3d, d3d8) с
метками времени, поэтому их можно сопоставлять между собой.

## Выводы, которые из этого следуют

### 1. Открытая сцена — это тысяча draw call'ов на кадр

10501 draw'ов в секунду при 6.5-10.5 fps даёт **порядка 1000 вызовов на кадр**.
Для сравнения, на вступительном экране при 60 fps было 11616 в секунду, то есть
около 190 на кадр. Разница между «терпимо» и «6.5 fps» — примерно пятикратный рост
числа вызовов, а не какая-то одна настройка.

Каждый вызов — это x86-код под box86 плюс пакет в command stream. Отсюда же
`wined3d_cs` на 68% ядра.

### 2. GPU в открытой сцене тоже упирается

Ожидание GPU выросло 7.7 → 10.5 → 16.8 → 21.7 → **31.7 мс на кадр** по мере
открытия вида. Это уже не «GPU скучает», как было на фиксированном споте в #26:
в открытой сцене чип считает кадр 31 мс. Поэтому асинхронный презентер (перекрытие
CPU и GPU) здесь спрячет часть этого времени, но не устранит его.

### 3. Линковка шейдеров подтверждена как источник рывков в сотни миллисекунд

280-590 мс на одну программу, четыре программы за секунду в момент входа в
локацию. Кадры 245 и 423 мс из гистограммы — это оно.

**Но кэш бинарных программ на этом стеке не реализуем со стороны PE.** Замерено:
блоб сообщает `binary_formats=1`, то есть умеет, а `glGetProgramBinary` и
`glProgramBinary` не резолвятся ни через `wglGetProcAddress` (ни desktop-, ни
OES-спеллинг), ни через экспорты `opengl32.dll`. Это ровно тот же барьер, который
уже задокументирован в `dlls/wined3d/texture_gl.c` для функций
ARB_ES2_compatibility: указатели существуют и `eglGetProcAddress` их отдаёт, но
unix-сторона Wine закрывает их по строкам расширений desktop GL, которых GLES-
контекст не объявляет.

Значит путей два, и оба вне PE-кода:

- правка unix-стороны `opengl32`, чтобы эти точки входа доходили до PE — та же по
  типу операция, которой сделан работающий `opengl32_glesver1.so`;
- либо прогрев: записать сгенерированные GLSL-источники на первом прогоне и
  линковать их при загрузке уровня, а не в кадре. Это не убирает 300-590 мс, а
  переносит их в загрузку, и не требует бинарников вообще.

### 4. Многосекундные остановки — отдельное явление, и оно НЕ объяснено

Кадры 10596 мс, 5872 мс, 1818 мс не покрываются линковками: в тех же окнах
суммарная линковка была 1.1-1.3 с. То есть это что-то третье.

Проверить не удалось: на этом ядре нет `/proc/<pid>/io` (нет
`CONFIG_TASK_IO_ACCOUNTING`), а счётчик чтения всего устройства
(`/sys/block/mmcblk0/stat`) в статичной сцене показывает ноль. Свап исключён
(нулевые `pswpin`/`pswpout`), нехватка памяти тоже (280 МБ свободно, 910 major
faults за всё время).

Остаются: подгрузка ассетов локации с SD-карты (мерить дельтами
`/sys/block/mmcblk0/stat` **во время** перехода), собственные загрузочные паузы
игры, и срабатывания теплового сторожа. Это первое, что надо снять следующим
прогоном.

### 5. Тепловой потолок съедает почти половину процессора

`cap=1104000` при 83.3 °C на зарядке. Это 45% ниже доступных 1992. Механизм
самоусиливающийся: открытая сцена греет сильнее, сторож режет частоту, сцена
становится ещё тяжелее. Владелец видит это как «в открытом месте всё падает».

## Что делать дальше, по отдаче

1. **Уменьшить число draw call'ов.** Это единственный рычаг, который бьёт
   одновременно по CPU и по GPU в открытой сцене. Батчинг подряд идущих
   совместимых draw'ов (`GL_EXT_multi_draw_arrays`, если он есть на блобе) —
   безопасный первый шаг; LOD/culling дальней геометрии — более сильный, но
   меняет картинку.
2. **Снять тепловой замер без зарядки** и понять, сколько из просадки — троттлинг.
   Это бесплатно и может оказаться крупнее любого патча.
3. **Разобраться с многосекундными остановками**: дельты `/sys/block/mmcblk0/stat`
   во время перехода в локацию, и отдельно лог сторожа
   (`/tmp/mgs2-thermal-guard.log`) с метками времени против гистограммы кадров.
4. **Линковка шейдеров**: правка unix-стороны `opengl32` для доступа к
   program-binary, либо прогрев по записанным источникам.
5. **Асинхронный презентер** — теперь понятно, что он спрячет часть из 31.7 мс,
   но не всё, потому что GPU реально занят. Ниже приоритетом, чем draw call'ы.

## Оговорки к этим числам

- Всё снято **на зарядке**, при потолке 1104 МГц; без зарядки картина будет иной.
- Заставку снять не удалось, так что про заставки в этом брифе данных нет.
- Диагностические каналы (три строки в секунду) писались в `/tmp`, то есть в
  tmpfs, а не на карту: 212 КБ за прогон, влияние на кадры исключено.

## Дополнение: prewarm из исходников не работает на этом драйвере

Проверено прямо (`MGS2_LINK_TWICE=1`): сразу после первой настоящей линковки
создаётся вторая программа из **тех же** объектов шейдеров и линкуется снова.

```text
MGS2 LINKTWICE first=198.7 ms second=194.7 ms status=1 shaders=2
```

Вторая линковка стоит столько же. Блоб Mali не кэширует результат по исходнику,
поэтому «слинковать всё заранее на загрузке» не помогает: wined3d ищет программу
по своему ключу состояний, а не по тексту шейдера, и при появлении комбинации в
кадре вызовет `glLinkProgram` заново — снова на 195 мс.

Следствие для плана: из двух вариантов приоритета 1 остаётся только один.

1. **Бинарный кэш через unix-сторону** — добавить thunk'и
   `glGetProgramBinaryOES` / `glProgramBinaryOES`, резолвя их нативным
   `eglGetProcAddress`, и вызывать из wined3d напрямую. Блоб сообщает
   `binary_formats=1`, то есть умеет; барьер только в мосте Wine, и он
   задокументирован в `dlls/wined3d/texture_gl.c` для функций
   ARB_ES2_compatibility. Прецедент правки unix-стороны в проекте есть —
   `opengl32_glesver1.so`. Это единственный вариант, который переживает
   перезапуск игры.
2. **Prewarm, наполняющий кэш самого wined3d** — проигрывать записанные
   комбинации состояний через `set_glsl_shader_program` на загрузке уровня, чтобы
   в rb-дереве появились записи, которые кадр потом найдёт. Суммарное время
   линковок не уменьшается, оно переезжает в загрузку. Работы существенно больше,
   выигрыш только внутри сессии.

Вариант «prewarm по исходникам без ключей состояний» из плана исключён.
