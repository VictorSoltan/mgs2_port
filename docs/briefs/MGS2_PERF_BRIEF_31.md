# MGS2 RG353VS — бриф #31: итог сессии и смена основного трека на Hangover

Дата: 7 августа 2026. Этот бриф закрывает линию «выжать проценты из текущего
Box86/Wine-стека» и фиксирует решение перевести основной трек проекта на
**Hangover**. Технические подробности замеров — в #30; здесь итог и решение.

## Итог сессии одной строкой

По кадрам — **ноль**. Закрыто два направления из плана, построены и проверены
приборы, восстановлены патчи. Ключевой замер (лестница A/B/C) не сделан и, по
решению владельца, **отложен**: он отвечает на менее важный вопрос, чем Hangover.

## Что закрыто окончательно

| направление | как закрыто | статус в плане #29/#30 |
|---|---|---|
| тепло, игра без зарядки | idle 64 °C, трип ядра 83 °C, насыщение <1 мин независимо от питания | был **пункт 1**, «бесплатно и крупнее всего» |
| пороги сторожа 84 → 86 | ядро режет своим трипом с 83 независимо от наших порогов | предлагалось в #29 |
| D3D8 sysmem VB/IB uploads | счётчики **ровно 0** при 8878–13987 draws/сек | был **P1** |

Оба закрытых направления были из дешёвых. Осталось дорогое — это и есть причина
смены трека.

## Арифметика, из которой следует решение

```text
тяжёлый Plant: ~103 мс CPU на кадр
24 fps  ->  41.7 мс  ->  нужно в 2.5 раза меньше CPU
30 fps  ->  33.3 мс  ->  нужно в 3.1 раза меньше CPU
```

Ни один из оставшихся мелких кандидатов — дедупликация ссылок на ресурсы,
resampler DSound, spin в игровом цикле, PGO, Box86 под A55 — не даёт
двух-трёхкратного сокращения. Это единицы процентов каждый, и даже вместе они
разрыв не закрывают. Двукратно-трёхкратно могут дать только:

1. **рисовать меньше** — батчинг, culling, разрешение (последнее измерено и
   работает, владельцем отклонено);
2. **сменить архитектуру исполнения** — Hangover;
3. **физическое охлаждение** — чтобы любой выигрыш по частоте закрепился.

## Решение: основной трек — Hangover, мелкие оптимизации приостановлены

Ключевое отличие:

```text
СЕЙЧАС                          HANGOVER
MGS2 i386                       MGS2 i386
  -> Wine i386 PE                 -> WowBox64
  -> Wine/Unix часть              -> Wine WoW64
  -> Box86 / Box64                -> НАТИВНАЯ AArch64 Unix-сторона
  -> ARM64 Linux / Mali           -> ARM64 Linux / Mali
```

Игровая логика остаётся x86 — чуда не будет. Но Wine перестаёт исполняться через
эмуляцию, а это то, чего мы ни одним патчем не добьёмся.

Отдельно важное для нас: сейчас мы обязаны жить с pbuffer/glReadPixels/wl_shm
из-за ABI-стены «x86 libwayland против нативного Mali EGL» (тупик из #29). С
нативной AArch64 Unix-стороной впервые возможна цепочка
`ARM64 WineWayland -> ARM64 libwayland -> ARM64 EGL/Mali`, то есть шанс выбросить
самый неприятный обход презентера целиком.

Точка входа выбрана **Hangover 11.0** — та же основная версия Wine, что и наш
стек, то есть минимальный diff при переносе патчей. Hangover 11.9 (Box64 0.4.2)
пробуем **после** того, как 11.0 заработает и появится baseline.

## План H0–H4, критерий решения на H3

```text
H0  отдельный wineprefix-hangover и launch-hangover.sh; production не трогаем,
    никаких bind-mount поверх рабочего Wine
H1  первое окно вообще без наших performance-патчей: prefix, launcher, меню,
    WineWayland создаёт окно
H2  первый настоящий D3D8-кадр; переносим ТОЛЬКО минимум (wined3d, GLES-фиксы
    opengl32/win32u). Ни DSound, ни PeekMessage, ни телеметрию
H3  СРАЗУ benchmark, до дальнейшего переноса
H4  только после положительного H3 — патчи по одному, каждый со своим A/B
```

Критерий на H3, фиксированный заранее, чтобы не подгонять его под результат:

```text
< 5%     архитектурной магии нет; думать, нужен ли Hangover вообще
5-15%    интересно, переносим только самые дешёвые оптимизации
15-25%   продолжаем однозначно
> 25%    текущий Box86-стек и был одним из главных bottleneck'ов
> 40%    Hangover становится основной платформой проекта
```

Смысл жёсткого H3: не потратить неделю на feature parity, чтобы потом узнать,
что выигрыш 4%.

## Какие из 11 патчей переносить, а какие сначала выбросить

Наши модули делятся на две разные группы. PE-DLL (`i386-windows/*.dll`) имеет
смысл сначала попробовать **как есть** — WoW64 для этого и предназначен.
А `i386-unix/*.so` в AArch64 Wine переиспользовать нельзя, и именно среди них
лежат обходы, которые существовали **из-за** архитектуры Box86.

```text
d3d8_mgs2fast1.dll      попробовать существующий i386 PE
wined3d_release3.dll    попробовать существующий i386 PE
user32_peek1.dll        НЕ ставить сначала, потом A/B
dsound/dmime/dmsynth    оставить на потом
winewayland_stall1.so   НЕ переносить: сначала проверить stock ARM64 WineWayland
ntdll_fastyield.so      НЕ переносить: стоимость этого пути в Hangover другая
win32u_glfuncs3.so      возможно нужен ARM64-аналог, если upstream не хватит
opengl32_glesver1.so    возможно нужен ARM64-аналог
```

Ожидание: из одиннадцати реально понадобятся пять-шесть. Перенос — заодно способ
выбросить исторический багаж.

Дополнительные бесплатные A/B после первого 3D: **WowBox64 против FEX**, и затем
**Hangover 11.0 против 11.9**. Победителя заранее не назначаем.

## Что остаётся жить из текущего трека

Приостановка не значит выбрасывание:

- Лестница A/B/C собрана, развёрнута и проверена живьём (26.6 → 41.4 → 24.7 fps
  при переключении ступени на ходу). Раннер `harness/ladder_run.sh`, спот —
  сейв `Game Data 02`. Готово к запуску в любой момент.
- Телеметрия ссылок на ресурсы (`MGS2_WINED3D_REFSTATS`) ни разу не снята.
- Разбор игрового цикла из #30 (`0x8a1ea0`, недостижимый `Sleep`, пять спинов на
  QPC) от смены стека не зависит и в Hangover останется верным.

## Открытое противоречие, не закрытое

Главная историческая победа проекта — «+29% от 1608 → 1992». Но защёлка сторожа
срезает потолок до нижней ступени за четыре секунды, значит верхняя ступень в
реальной игре почти ничего не должна давать. Одно с другим не сходится, и какая
из двух цифр верна — неизвестно. Стоит перепроверить, потому что на этой цифре
стоит вся тепловая часть истории оптимизации.

## Операционное, что стоило времени и повторится

```text
launch.sh держит single-instance flock и намеренно утекает fd 9 в службы Wine.
    Осиротевший rpcss.exe после kill игры продолжает держать lock, и следующий
    запуск выходит с кодом 0 БЕЗ сообщений. Ни comm игры, ни шаблон wine* его
    не находят. Проверять сам lock через /proc/*/fd
диск был заполнен на 100% (160 КБ свободно). Игра при нуле свободных блоков
    отказывается сохраняться -- ровно поэтому D: смонтирован на /storage.
    Освобождено 789 МБ: 621 МБ чужих логов отладки и 168 МБ вариантов wined3d,
    на которые launch.sh не ссылается (все есть в device-artifacts)
release-объекты wined3d новее исходников, make их молча не пересобирает
scaling_max_freq пишет и ядро через cooling_device0, не только наш сторож
```
