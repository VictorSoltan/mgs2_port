# MGS2 RG353VS — полный фриз на patch 27 (separable stages), живой захват

Дата: 12–13 августа 2026. Статус: фриз захвачен живым на устройстве, механизм
измерен, **причина не атрибутирована**.

Состояние production на конец 13 августа, проверенное побайтово:

```text
в production   патчи 26, 27, 28, 29, плюс box86 01-03; ntdll (05) снят;
               SAFEFLAGS вернулся к дефолту 1; CALLRET=1 оставлен
НЕ в production патч 30 (выключен, измерено: в геймплее не даёт ничего),
               патч 31 (ОТКАЧЕН 13 августа: замер был на нерепрезентативном
               маршруте, вживую игра стала хуже — раздел 6l),
               box86 04 (оформлен, дерева исходников Box86 здесь нет)
```

Что известно про сами фризы: они первого использования — новая сцена или новая
модель врага, потом стабилизируется. Линковка программ даёт 4.5–4.7 с за прогон
из ~11.8 с остановок (раздел 6j с поправкой 6k). Вторая половина не названа.

Это третий по счёту no-render/input стоп в проекте и он **отличается от двух
предыдущих**: это не PeekMessage-спин (brief runtime bug capture) и не
Box86 aligned-mutex first-use race (brief runtime mutex freeze) — тот box86
с фиксом здесь смонтирован и подтверждён побайтово.

## 1. Наблюдение

Игрок сообщил о полном зависании посреди геймплея, «много врагов в кадре».
Процесс на момент захвата ещё жил, не был убит и не был перезапущен — весь
раздел 2 снят с этого самого инстанса.

Сессия: старт в 11407.77 с boottime, захват на 12981 с, то есть фриз наступил
внутри примерно 26 минут геймплея.

## 2. Живой захват

Один инстанс (`comm = mgs2_sse_rg353v`, pid 24615), маунты на месте, побайтовая
сверка точек монтирования:

```text
/usr/lib/wine/i386-windows/wined3d.dll  == wined3d_finalplay_separable.dll   OK
/usr/lib/wine/i386-unix/opengl32.so     == opengl32_finalplay_sso.so         OK
/usr/bin/box86                          == box86-native-memmove3             OK
                                           (35da6977..., как в SHA256SUMS)
```

`MGS2_GL_SEPARABLE` в окружении процесса отсутствует, то есть separable-путь был
включён (политика patch 27: включён по умолчанию). `MGS2_GPU_PROBE` тоже
отсутствует — **кольцо замеров было выключено, данных пробника по этому фризу
нет**.

### Ни один поток не крутится

Все 25 потоков в состоянии `S`. Три самых тяжёлых потока не сдвинулись ни на
один тик за ~10 минут наблюдения (три независимых чтения `/proc/<tid>/stat`):

```text
tid    comm              utime   stime   состояние
25290  mgs2_sse_rg353v   82679    9646   futex, без изменений
25267  wined3d_cs        67111    4544   futex, без изменений
25242  mgs2_sse_rg353v   26706    3805   ioctl, без изменений
24615  mgs2_sse_rg353v    3863→3903      ntsync WAIT_ANY, ЖИВ (~13% CPU)
```

Главный поток продолжает крутить `NTSYNC_IOC_WAIT_ANY` (`ioctl` cmd
`0xc0284e82` = `_IOWR('N', 0x82, …)`, 40 байт) и потому накапливает время —
поэтому load average падал (0.70 за минуту против 2.69/2.74 за 5/15), но кадры
не идут: renderer запаркован навсегда.

### Ожидание, из которого нет выхода

`/proc/<tid>/syscall` для двух запаркованных потоков:

```text
25267  240 (futex)  uaddr=0x400f012c  op=0x80  val=0  timeout=NULL
25290  240 (futex)  uaddr=0x400f0158  op=0x80  val=0  timeout=NULL
```

`op=0x80` = `FUTEX_WAIT_PRIVATE`, `timeout=NULL` — **ожидание без таймаута**.
Оба слова futex прочитаны из `/proc/<pid>/mem` и равны нулю, то есть условие
ожидания всё ещё выполняется и разбудить эти потоки уже некому: потерянный
wakeup, а не медленная работа.

Оба адреса лежат в одном анонимном регионе `0x400f0000-0x40100000` (rw-p, 64 KiB),
сразу за страницами bridge/thunk Box86 (`0x40010000`…`0x400e1000`, rwxp — именно
там сидят GL-указатели из `mgsdbg.log`, напр. `glLinkProgram -> 0x40020bb0`).
Два потока ждут на соседних словах одного и того же пула синхронизации Box86,
на расстоянии 0x2c друг от друга.

### Это ожидание не мьютексное

`val=0` означает «спать, пока слово равно нулю», то есть ждать, когда оно станет
**ненулевым**. Contended-мьютекс glibc ждёт обратного — `val=2` на `&m->__lock`.
Такая форма принадлежит семафору или событию (`sem_wait` при нулевом значении),
а не захвату мьютекса.

Практическое следствие: смонтированный `box86-native-memmove3` действительно
несёт `box86-patches/03-aligned-mutex-publication.patch` (это подтверждено и
брифом runtime mutex freeze, и SHA), но тот патч правит публикацию
`pthread_mutex_t`, и с механизмом текущего фриза он не совпадает. Фриз 2026-08-12
**не является рецидивом дефекта 2026-08-11**, хотя и живёт в том же пуле Box86.

Kernel stack обоих — чистый `__futex_wait → futex_wait → do_futex →
__arm64_sys_futex_time32`, PC в обёртках `libc.so.6`. Разворот user-стека по
`sp` информации не дал (у 25290 окно 1.5 KiB однородно заполнено одним
указателем `box86+0x332bf4`, кадров вызовов там нет) — дальше без символов
Box86 не пройти.

## 4. Атрибуция: что измерено, а что нет

**Измерено.** Дельта развёрнутой конфигурации относительно последней
зафиксированной рабочей (`84aab7e`) — ровно два файла patch 27: `wined3d` и
`opengl32`. Всё остальное в цепочке идентично FINALPLAY3, который до этого
держал длинные сессии.

**Не измерено, это гипотеза.** Что фриз вызван patch 27. Пробник был выключен,
воспроизведения с A/B нет. Правдоподобный механизм: много врагов в кадре — это
много новых перестановок шейдеров, а separable-путь на каждую пару создаёт
втрое больше GL-объектов (stage-программа VS + stage-программа PS + pipeline)
и вносит **новые вызовы в горячий путь**: `mgs2_glActiveShaderProgram()` дважды
за `shader_glsl_load_constants()` плюс `mgs2_resolve_separable()` там же. Больше
объектов и больше вызовов драйвера — больше first-use публикаций синхронизации
в libmali/Box86-мосту. Но связь именно с потерянным wakeup не показана.

**Свидетельство игрока, не измерение.** Небольшие фризы, по словам игрока,
появились раньше — после одного из более ранних оптимизационных патчей, а не
после patch 27; тогда длинные сессии просто не игрались, и полные зависания
проявились только когда играть стали подолгу. Если это так, patch 27 —
последнее изменение, но не автор симптома, и приоритет смещается на более раннюю
оптимизацию. Конкретный патч ещё не назван; до его выяснения раздел 7 держит
шаг 1 первым именно поэтому.

Оговорка против собственной гипотезы: сигнатура (два потока на соседних словах
пула Box86, untimed wait, нулевые слова) принадлежит семейству
aligned-mutex-дефектов, а не шейдерному коду как таковому. Patch 27 в этой
рамке — не автор дефекта, а нагрузка, которая его вытаскивает. Различить эти два
объяснения этим захватом нельзя.

## 5. Ловушка: `MGS2_GL_SEPARABLE=0` не является полным A/B

Раздел 8 брифа transition hitch фиксирует, что в production монтировался
`opengl32_glesver1.so`, а `opengl32_finalplay_sso.so` собран из ветки
**glesver2**, и регресс glesver1 → glesver2 (opt-in base-vertex путь патча 19)
отдельно не проверялся. Значит развёртывание изменило **две** вещи, а не одну.

`MGS2_GL_SEPARABLE=0` выключает только separable-логику в wined3d, но
`opengl32_finalplay_sso.so` остаётся смонтированным. Эта переменная не
возвращает систему в известное рабочее состояние и как инструмент атрибуции
даст неверный ответ, если виноват второй фактор.

## 5a. Измерено: какая часть GLES-моста действительно несущая

В ходе разбора было заявлено, что «GLES-фасад — фундамент, откатить его нельзя,
A/B для него не существует». **Это проверено на устройстве и в основном неверно.**
Три прогона, лабораторный лаунчер с условными маунтами, всё остальное идентично,
`MGS2_GL_STATS=120`, `WINEDEBUG=err+all`, судьба кадра по строкам
`MGS2 present stats` и по снимку `grim`.

```text
плечо                                       present stats   картинка
A  прод целиком                             35 окон, 60.4 fps   титул, корректно
B  без opengl32_glesver1.so (stock Wine)     35 окон, 60.4 fps   корректно
C  без win32u_glfuncs3.so (stock Wine)       0                   нет вообще
```

Плечо B: игра грузится и рисует **без** патча 06. Его дефект при этом реален и
виден — `err:opengl:parse_gl_version Invalid OpenGL major version 0` встречается
3 раза в B и 0 раз в A, то есть разбор строки `"OpenGL ES 3.2 ..."` действительно
ломается и патч действительно его лечит. Но на получение контекста и на
отрисовку это не влияет, и per-frame разницы в этом плече не видно.

Плечо C: контекста нет совсем.

```text
err:d3d:wined3d_adapter_gl_init    Failed to get a GL context for adapter
err:d3d:wined3d_caps_gl_ctx_create Failed to find a suitable pixel format
```

Это тот же отказ, что записан в разделе 5 брифа transition hitch про пересборку
win32u, и теперь он воспроизведён прямой заменой модуля.

Выводы, которые из этого следуют для расследования фризов:

- Несущий модуль — `win32u_glfuncs3.so` (патч 08), а не `opengl32` (патч 06).
- «A/B невозможен» было неверно: он стоит одной переменной окружения и ~2 минут
  на плечо. Патч 06 можно снимать и играть, поэтому как подозреваемый по фризам
  он проверяем обычным способом.
- `device/mgs2_egl_facade.c` к этому вообще не относится: по брифу #33 это
  aarch64-шим, подставляемый как `libEGL.so.1` для ветки Hangover, чтобы не
  трогать её stock. К продовому пути под Box86 он не подключён.
- Для `win32u` дешёвого A/B нет: снятие даёт не медленную игру, а отсутствие
  картинки. Если подозрение ляжет на него, работа — искать дефект внутри.

Воспроизведение: копия `launch-play.sh` с двумя условными маунтами лежит на
устройстве как `launch-lab-facade.sh`; переключатели `LAB_SKIP_OPENGL32=1` и
`LAB_SKIP_WIN32U=1`. Это лабораторный файл, не production, и внешний враппер
меню его не вызывает.

## 6. Откат, выполненный 2026-08-12

Игра остановлена по процедуре DEVICE.md, все bind-mount'ы размотаны (проверено:
ни одного остатка в `/proc/mounts`), процессов не осталось, кэп восстановлен на
1992000.

```text
device (устройство):  launch-play.sh <- launch-play.sh.pre-separable
                      подозрительный сохранён как
                      launch-play.sh.bak-20260812-separable-freeze
repo:                 device/launch-play.sh возвращён к glesver1 + finalplay
сохранено:            wine-patches/27-separable-shader-stages.patch,
                      оба бинарника и их контрольные суммы в SHA256SUMS
```

Цена откатa известна и мала: patch 27 давал 116 ms вместо 201 ms на пару
программ (−42%, около 2.4 с снятых пауз за сессию). Per-frame throughput он не
трогает, поэтому измеренные 30 fps на тяжёлом споте откат не задевает.

### Откат отменён в тот же день

Патч 27 возвращён в production 2026-08-12, потому что основание для его снятия
рассыпалось: он был снят как самое свежее изменение, а затем выяснилось, что
фризы ему предшествуют (раздел 4, свидетельство игрока), и захват не совпал ни
с одним из двух ранее закрытых дефектов. Обмен сознательный и записан здесь,
чтобы его не пришлось выводить заново: постоянный измеренный выигрыш против
редкого неатрибутированного фриза. `launch-play.sh` снова монтирует
`wined3d_finalplay_separable.dll` и `opengl32_finalplay_sso.so`.

Плечо 6a (мост memmove) свёрнуто по решению игрока: ждать редкого фриза как
рабочий процесс непрактично. Мост возвращён в `=1`.

**Итог дня, без прикрас: ни один патч не удалён и фриз не исправлен.** Продукт
дня — характеристика механизма, список исключённого (раздел 3), два закрытых
ложных следа (раздел 5a), инструмент захвата и две письменно исправленные
собственные ошибки. Единственный найденный бесполезный элемент стека —
`ntdll_fastyield.so`, см. раздел 8.

## 6a. Плечо 1 поиска фриза: мост native memmove выключен (СВЁРНУТО)

**Плечо не доведено и результата не дало.** Оно было запущено и проверено на
однофакторность, но свёрнуто до появления данных: ждать редкого фриза как рабочий
процесс непрактично. Раздел сохранён потому, что настройка плеча и способ его
судить остаются в силе, если к нему вернутся.

Запущено 2026-08-12, после того как игрок сообщил, что фризы появились задолго до
патча 27. Первым снят единственный снимаемый элемент, который трогает Box86 —
именно там висел захваченный futex.

```text
MGS2_BOX86_NATIVE_MEMMOVE=0     мост выключен
box86                            остался box86-native-memmove3, файл не подменён
opengl32/win32u                  на месте, побайтово сверены (см. 5a: несущие)
MGS2_GL_STATS=300                fps пишется
WINEDEBUG=-all,err+waylanddrv    только строки статистики: 76 строк лога вместо
                                 38 562 при err+all
```

Однофакторность проверена: в box86 мост ставится только при
`getenv("MGS2_BOX86_NATIVE_MEMMOVE") && atoi(...)`, поэтому `0` его отключает без
подмены бинарника. Продовый `launch-play.sh` перезаписывает переменную жёстко
(`export ...=1`), поэтому плечо гоняется через `launch-lab.sh` на устройстве.

Как судить это плечо. Фриз был **один раз за 26 минут**, поэтому одна чистая
сессия ничего не доказывает; отсутствие фризов копится в пользу подозреваемого
только с наработкой. Решает совпадение сигнатуры: при любом фризе снять
`freeze_capture.py` и сравнить с разделом 2. Совпал untimed futex в арене
Box86 — мост невиновен, идём к следующему плечу.

Цена по производительности измеряется тем же логом: ориентир из брифа #43 —
30.0/30.0/30.1 fps на фиксированном тяжёлом споте при 1992 МГц **с включённым**
мостом. Значения на интро (57–60 fps) для сравнения не годятся: сцена другая.

## 6b. Плечо 2: минимальный стек, деление стека пополам

Идея игрока, и она сильнее перебора по одному патчу: снять **всю** цепочку
оптимизации рендерера сразу, оставив фундамент. Если фриз воспроизведётся на
такой конфигурации, из подозреваемых одним ударом выпадают патчи 12 и 18–27, и
причина остаётся в фундаменте — box86, мост GLES, libmali.

`launch-min.sh` на устройстве, лаборатория, не production. Развёрнуто 2026-08-12.

```text
ОСТАВЛЕНО                         ЧТО ЭТО ЗНАЧИТ
win32u_glfuncs3.so                мост GLES линии CrossOver; несущий (раздел 5a)
opengl32_glesver1.so              разбор версии GLES; несущий (раздел 5a)
winewayland_stall1.so             путь вывода кадра
box86-native-memmove3             отдельная ось, не эта
dmime/dsound/dmsynth/dmusic       аудио, чтобы не ловить регресс звука

СНЯТО
wined3d_release3.dll   вместо finalplay_separable  -> нет патчей 12, 19, 25, 27
                                                      и всего MGS2BATCH/MGS2CACHE
d3d8_mgs2fast1.dll     вместо finalplay2           -> нет патча 26 и серии 18-24
штатный user32                                     -> нет патча 07
штатный ntdll                                      -> нет патча 05 (снят ранее)
```

Проверено после запуска: три модуля сверены побайтово, `user32` и `ntdll` в
`/proc/mounts` отсутствуют, маунтов 10 вместо 11, `page fault` ноль.

Стек согласован, а не собран из несовместимых эпох: за прогон **ни одной**
`GL_INVALID_*` через `wined3d_check_gl_call`, картинка визуально корректна
(снимок в `logs/live-20260812/`).

**Цена, измеренная сразу.** Одна и та же сцена (демо в коридоре):

```text
production (патч 27 + вся цепочка)   57-60 fps
минимальный стек                     45.4 -> 23.7 -> 11.6 fps
```

То есть до пяти раз медленнее. Это ожидаемая плата: 30 fps на тяжёлом споте
брифа #43 приходили именно из снятой цепочки. Играть на этом плече заметно
хуже, и это не дефект конфигурации.

### Результат плеча 2

Сохранения грузятся — это подтверждает раздел 5a с другой стороны: падения на
загрузке давал именно снятый фасад `opengl32`, а не что-либо ещё.

Игрок сообщил «фризы так же есть». Гистограмма времени кадра за его сессию
(`MGS2_GL_STATS=300`, 40 окон):

```text
худший кадр            8679 ms
следующие              4865, 2861, 1306, 1260 ms
кадров дольше 500 ms   6 за сессию
медиана окна           5279 ms на 300 кадров (~57 fps)
```

То есть многосекундные остановки на этом плече реальны и измерены.

**Но плечо не даёт того вывода, ради которого затевалось.** Проверка в момент
жалобы: процесс жив, состояние `R`, 55–57 fps. Значит воспроизвелись
**восстанавливающиеся** остановки, а не постоянный дедлок раздела 2, который не
отпускает и требует убить процесс. Это два разных явления.

Более того, для восстанавливающихся остановок минимальный стек — заведомо плохой
судья: снята вся работа, которая их смягчала, включая патч 27. 8.7 с похожи на
десятки линковок подряд по ~200 мс. Поэтому:

```text
патчи 12 и 18-27 НЕ вычеркнуты; постоянный дедлок на плече 2 не воспроизведён
восстанавливающиеся остановки на плече 2 ожидаемо хуже, а не показательны
```

### Визуальная поломка на плече 2 — ошибка конфигурации, не снятие патчей

Портрет кодека не рисовался. Причина: `launch-play.sh` сознательно не выставляет
env-переключатели, потому что в FINAL-сборках политика вкомпилирована, а
`wined3d_release3` читает их из окружения. Минимальный лаунчер собирался из
продового и потому не передал `MGS2_GLES_FBO_READBACK=1` — тот самый «GLES-safe
FBO capability probe» для цели портрета кодека, документированный в `launch.sh`.
Добавлено вместе с `MGS2_SKIP_CODEC_BLACK_QUAD=0`.

Урок на будущее: **лабораторные плечи собирать из `launch.sh`, а не из
`launch-play.sh`.** Продовый лаунчер по устройству неполон для не-FINAL сборок,
и это его свойство, а не дефект.

## 6d. Смена цели: многосекундные остановки, и чем они инструментованы

Измерение, которое сменило цель поиска. Худший кадр за сессию:

```text
минимальный стек (снято 12 патчей)   8679 ms
полный прод (все патчи на месте)     6591 ms, рядом 6007 ms
```

Остановки на 6-8 секунд переживают и снятие двенадцати патчей, и наличие всех.
Значит они **не объясняются набором патчей**, который перебирался весь день, и
тем более не линковкой шейдера: самая дорогая измеренная линковка — 329 мс.
Дальнейшее снятие патчей к причине не ведёт; это записано, чтобы к нему не
возвращались.

Запущено `launch-probe.sh`: конфигурация с патчем 27, то есть **та самая, в
которой измерены 6591 мс**, но с неструпленной `wined3d_separable_v9_probe.dll`
и `MGS2_GPU_PROBE=1`. Три независимых сигнала:

```text
/tmp/probe.log    fps + гистограмма времени кадра (worst, 50/100/200/500 ms)
кольцо в памяти   compile_shader / link_program / link_separable_stage /
                  validate_program_pipeline / slow_bind, с длительностями
                  harness/gpu_transition_probe.py --symbol-vma 0x101f4160
/tmp/iomem2.log   majflt, VmRSS, VmSwap, MemAvailable, SwapFree, секторы mmcblk0
```

`sample_io_mem.sh` читает четыре файла `/proc` раз в 2 с и не разворачивает
стеки, в отличие от `stall_watch*` — правило 2 соблюдено. `/proc/<pid>/io` на
этом ядре отсутствует (собрано без `CONFIG_TASK_IO_ACCOUNTING`), поэтому трафик
карты берётся системно из `diskstats`.

База на старте: `majflt=63` и не растёт, `VmSwap=0`, `MemAvailable` 206 МБ.

Как читать результат после очередной остановки:

```text
в кольце сумма link/compile ~= длительности остановки  -> всё-таки шейдеры
скачок majflt / падение SwapFree                       -> подкачка с SD
скачок rd_sec без majflt                               -> чтение данных игры
ничего из перечисленного                               -> box86/dynarec или GPU,
                                                          и тогда это первый
                                                          подозреваемый вне Wine
```

Ловушка, на которую я наступил при настройке, чтобы её не повторили:
`pgrep -f sample_io_mem.sh` матчит саму ssh-команду, в строке которой есть это
имя, и `pkill` по такому шаблону убивает собственную сессию. Останавливать
сэмплер только по PID.

## 6e. Аудит по счётчикам: что реально работает, и первое удаление по числам

Вопрос был поставлен правильно: не «что можно снять без потери fps», а «что из
этого вообще работает». Ответ измерим за один прогон, потому что у путей есть
встроенные счётчики. Ловушка: **патч 25 их вырезал из FINAL-сборок** (в его диффе
`MGS2_BATCH_STATS`, `MGS2_D3D8_STATS`, `MGS2_D3D8_VISIBILITY_CULL_STATS` идут
минусами), поэтому телеметрия осталась ровно в двух архивных бинарниках:
`wined3d_batch16_setcache.dll` и `d3d8_producer_batch20_visibilitycull.dll`.

Прогон `launch-audit.sh`, 300 кадров:

```text
MGS2CULL   tested=112800 (376/кадр)  culled=33297 (111/кадр) = 29.5% отброшено
           cache_hit=0  cache_miss=112800        <-- кэш не попадает НИ РАЗУ
           source_bad=4471  invalid=0  overflow=0  nonfinite=0
MGS2BATCH  draws=9191 -> batches=384  factor=23.93  fps=31.74
MGS2CACHE  hits=288  misses=0  evict=0  entries=170
```

Вывод по каждому:

```text
батчер          24x меньше draw-вызовов — это и есть производительность, не трогать
MGS2CACHE       288 попаданий, 0 промахов, 0 вытеснений — работает как задумано
culler          отбрасывает 29.5% проверенного — работу делает
кэш AABB        МЁРТВЫЙ: 0 попаданий на 112 800 обращений
```

Кэш не мог попадать по построению: его ключ включает `mgs2_geometry_generation`,
который инкрементируется на каждом записывающем `Unlock`, а MGS2 переливает
динамические вершинные буферы каждый кадр — ровно поэтому существует патч 26.
Запись не доживает до следующего обращения никогда.

### Патч 28: кэш удалён

`wine-patches/28-drop-dead-cull-cache.patch`, применяется с `-F0`.
Собрано по рецепту README, задеплоено как `d3d8_finalplay3_nocullcache.dll`
(`841ff73c…`, записано в SHA256SUMS).

```text
.bss   74 464 -> 704 байт   (-73 760)
.text  52 368 -> 51 520     (-848)
```

Корректность: удаление не может изменить ни одно решение culler'а, потому что при
промахе старый код считал AABB этим же циклом, а промахи были всегда.

Проверено на устройстве: запускается, картинка есть, `page fault` ноль, классы
ошибок GL те же, что и на эталонной `finalplay2` при таком же логировании
(`GL_SAMPLE_ALPHA_TO_COVERAGE`, `GL_LINE_SMOOTH`, `depth clip`) — то есть новых
патч не внёс.

**Эффект на fps не измерен.** Окна пришлись на разные сцены демо-режима
(60/60/57 против 40/42/42), а правило 3 запрещает читать A/B по неравным сценам.
Патч только убирает работу, поэтому регресса не ожидается, но закрыть это может
только пара окон на фиксированном споте.

### Побочная находка, не закрыта

При включённом `err+d3d` эталонная сборка выдаёт 52 365 ошибок GL за ~2 минуты:
21 537 `glEnable GL_SAMPLE_ALPHA_TO_COVERAGE`, по 9 938 `glDisable(GL_LINE_SMOOTH)`
и `depth clip`. В production они невидимы, потому что ERR за проверкой канала, но
**сами вызовы происходят** и драйвер их отвергает. Это кандидат на следующий
патч: не выдавать на GLES состояние, которого там нет.

## 6f. Кампания взвешивания оптимизаций, 2026-08-12, автономно

Задача: найти оптимизацию, которая внесла остановки, и убрать те, что дают мало.
Пять плеч по 400–450 с на демо-режиме, метрика — гистограмма времени кадра.

**Демо детерминировано, и это оказалось главным инструментом.** Корзины
`кадров >50/>100/>200/>500 мс` вышли **побайтово одинаковыми — 31/9/11/4 — во всех
плечах**, а худшие кадры совпали в пределах 3%: 3468, 3555, 3428, 3548 мс и
рядом 2007–2114 мс. Значит остановки в демо воспроизводимы и A/B по ним валиден.

```text
плечо                                     окон  ср. fps  медиана  худший   >500мс
патч 27, dynarec как в проде                96    58.9    4993ms   3468ms      4
dynarec консервативный (3 ключа)            83    56.8    5161ms   3555ms      4

culler=ON  (архивная пара со счётчиками)     53    44.3    6948ms   5701ms      3
culler=OFF (то же, culler выключен)          43    37.7    9722ms   3492ms      4
```

### Что взвешено и что сделано

```text
culler (патч 24/25)     44.3 против 37.7 fps = +17.5%   ОСТАВЛЕН
                        Моё прежнее сомнение в его экономике снято измерением.
кэш AABB culler'а       cache_hit=0 / cache_miss=112800  УДАЛЁН (патч 28, в проде)
CALLRET=1               58.9 против 55.5 fps = +6.1%     ОСТАВЛЕН
SAFEFLAGS=0             58.9 против 58.4 = +0.9%, шум    СНЯТ, вернул дефолт 1
                        Понижал точность флагов x86 ради процента.
BIGBLOCK=2              измерен только в связке          ОСТАВЛЕН, не взвешен
```

### Из чего состоят остановки: измерено, и это не патчи

Кольцо пробника за 450 с, полная запись (129 событий, обёртки не было):

```text
link_program        n=12   сумма 2308.9 ms   макс 202.5 ms
slow_bind (op 10)   n=104  сумма  166.5 ms   макс   5.4 ms
compile_shader      n=13   сумма   34.1 ms
link_separable_stage  НИ ОДНОГО
```

Итого работа по шейдерам за прогон — **2.5 с**, тогда как остановок в том же
прогоне на 8–9 с. Один кадр в 3468 мс не объясним линковками даже теоретически:
их за весь прогон двенадцать. Подкачка: `majflt` 10 → 25 за 450 с. Карта:
14 488 секторов, около 7 МБ. То есть остановки **не шейдеры, не подкачка, не
чтение с SD и не ключи dynarec** — последние не сдвинули корзины ни на единицу.

Отдельно: separable-путь патча 27 в демо не сработал ни разу, все 12 линковок
монолитные. Его измеренный выигрыш получен на сессии с загрузкой сохранения и
кодеком, а не на этом сценарии; на демо он не проявляется.

### Нарушение правила 3 в этой кампании, и что из-за него шатается

Шесть плеч по 400–450 с гонялись подряд **без пина частоты**. К концу кампании
`scaling_max_freq` упал с 1992000 до 1608000, температуры дошли до 84.4 и 81.7 °C.
То есть поздние плечи мерились на более низком клоке, чем ранние. Порядок был:
`cull_on`, `cull_off`, агрессивный dynarec, консервативный, `SAFEFLAGS=1`,
`CALLRET=0`.

Что из выводов это шатает, честно:

```text
корзины остановок      НЕ шатает: 31/9/11/4 совпали во всех плечах независимо
                       от клока, что делает этот результат даже прочнее
SAFEFLAGS              НЕ шатает: плечо шло раньше и горячее эталона, то есть
                       нагрев работал ПРОТИВ него, а разница всё равно 0.9%
CALLRET=1 (+6.1%)      ПЕРЕМЕРЕНО и подтверждено: клок закреплён на 1416000,
                       оба плеча с остывшего старта (64 °C):
                         CALLRET=1  89 окон  58.83 fps  медиана 5013 ms
                         CALLRET=0  70 окон  55.53 fps  медиана 5400 ms
                       = +5.9% по fps и +7.7% по медиане. Ключ остаётся.
culler (+17.5%)        слегка: cull_off шло вторым, чуть горячее; направление и
                       величина разрыва сохраняются, но точное число не финальное
```

### Вторая методическая находка: демо упирается в кадровый лимит

При перемере обнаружилось важнее нагрева. На 1992000 средний fps был 58.9, на
закреплённых 1416000 — 58.83. Клок срезан на 29%, fps не изменился, а медиана
окна 5013 мс на 300 кадров — это 59.8 fps. **Демо-режим ограничен 60 fps**, и
большинство окон сидит на потолке.

Следствие для метрики: средний fps по окнам измеряет не пропускную способность, а
**как часто конфигурация проваливается ниже потолка**. Для CPU-side оптимизаций с
запасом это малочувствительно, и различия внутри пары процентов на демо читать
нельзя вообще. Плечи culler'а (44.3 и 37.7) от этого не страдают: они шли на
архивных неструпленных сборках, далеко от потолка.

Правильный полигон для перф-A/B остаётся прежним — фиксированный тяжёлый спот в
геймплее, где счёт идёт около 30 fps. Демо годится для остановок, а не для fps.

### Вывод, противоречащий исходной гипотезе

Ни одна переключаемая оптимизация остановки не вносит. Более того, **худший
профиль остановок дал самый неоптимизированный стек**: у минимального (раздел 6b)
6 кадров дольше 500 мс на 40 окон против 4 на 96 у полного прода, то есть
нормированно втрое хуже. Цепочка оптимизации остановки уменьшает, а не создаёт.

Остаётся необследованным: события загрузки сцены на стороне игры (гостевой код),
путь презентации и сам драйвер Mali. Это и есть следующее направление, а не
дальнейшее снятие патчей.

## 6g. Что на самом деле измеряли корзины остановок, и одна настоящая остановка

Продолжение кампании, 2026-08-13. Три результата, из которых первый отменяет часть
выводов раздела 6f.

### Корзины остановок в демо — это профиль запуска, а не остановки в игре

Прогон 470 с с посекундным сэмплером, стартовавшим раньше игры. Монотонный счётчик
кадров дольше 500 мс стоял на 4 **все 308 сэмплов**, а сами эти кадры пришлись на
строки 1, 2 и 10 из 441 строк гистограммы:

```text
окно 1    худший кадр 3024 ms
окно 2    худший кадр 3471 ms
окно 10   худший кадр 1066 ms
далее     430 окон, ни одного кадра дольше 500 ms
```

То есть все многосекундные остановки демо — первые ~20 секунд, разогрев первого
использования. Демо стартует одинаково каждый раз, поэтому корзины и совпадали
побайтово во всех плечах раздела 6f.

**Поправка к 6f:** «ни одна переключаемая оптимизация не влияет на остановки»
следует читать как «ни одна не влияет на разогрев запуска». Про остановки в
процессе игры те плечи не говорят ничего, потому что таких остановок в них не было.

### Демо не воспроизводит постоянный фриз

Один прогон продержался **8.4 часа**. Постоянного фриза не случилось ни разу.
Значит демо-режим для ловли фриза игрока не годится: ему нужен геймплей.

### Единственная настоящая остановка в процессе работы, разобранная по потокам

На 8.4-м часу посекундный сэмплер поймал её (и вторую такую же в другом прогоне):

```text
1786594559  всего 28 тиков
  работали только: data-loop.0:4  audio_client_ti:1  wine_dsound_mix:18
                   wine_dmsynth_si:1  wine_dmsynth_si:1  игровой мелкий:3
  ОТСУТСТВУЮТ:     главный поток, горячий игровой поток, wined3d_cs,
                   mali-cmar-backe
соседние сэмплы 76 и 102 тика — тоже провал, затем возврат к ~300
```

Вся графическая цепочка встаёт одновременно и **не потребляет CPU**, а звук идёт
на своей обычной скорости. Это ожидание, не вычисление, и оно общее для четырёх
потоков сразу.

Исключено измерением, каждое отдельным прогоном:

```text

glReadPixels      в окне с кадром 3343 ms readback 4.21 ms/кадр против
                  медианы 3.93 и максимума 4.82 по всем окнам -- не подскочил
шейдеры           вся работа кольца за 450 с = 2.5 с против 8-9 с остановок
```

## 6h. Чтение активных патчей: находки и честные отрицательные результаты

Многоагентный аудит выполнить не удалось — все десять агентов упали на лимите
расходов организации, результатов ноль. Ниже — то, что прочитано вручную, по одной
области. Каждая находка с `файл:строка` из **живого продового дерева**.

### Класс «падение и порча памяти»

**1. `box86-patches/02`, `src/tools/bridge.c`, `getAlternate()` — чтение за границей
маппинга.** Активно (`MGS2_BOX86_NATIVE_MEMMOVE=1`).

```c
if (mgs2_native_memmove && (uintptr_t)addr >= 0x10000 && getProtection((uintptr_t)addr))
{
    static const unsigned char signature[] = {0x56,0x57,0x8b,0x7c,0x24,0x0c, ... };  /* 20 байт */
    if (!memcmp(addr, signature, sizeof(signature)))
```

`getProtection()` проверяет отображённость **одного** байта, а `memcmp` читает
**двадцать**. Адрес в последних 20 байтах маппинга даёт нативный SIGSEGV внутри
box86, а не управляемую ошибку гостя. Сценарий: любой lookup альтернативы для
адреса у конца региона — а `getAlternate()` вызывается на каждом промахе таблицы.
Исправление: проверять отображённость всего сравниваемого диапазона.

**2. Тот же файл — подпись слишком родовая, редирект может уехать не туда.**
Двадцать байт `push esi; push edi; mov edi,[esp+0xc]; mov esi,[esp+0x10];
mov ecx,[esp+0x14]; mov edx,edi; sub edx,esi; cmp edx,ecx` — стандартное начало
всего семейства копирующих функций, которое компилятор порождает одинаково.
Совпадение проверяется без привязки к модулю, без проверки длины и без списка
разрешённых модулей. Любая другая функция с тем же прологом молча уедет в нативный
`memmove`, который вызовет её аргументы как `(dst, src, size)`. Сценарий: другой
вариант копирования в том же или чужом модуле. Исправление: сузить до конкретного
модуля и адреса, найденного один раз, вместо сканирования каждого lookup'а.

Замечание про цену: выигрыш моста записан как «31% сэмплов главного потока в
гостевом `_sse2_memmove`», но **в fps он не измерен ни разу**. То есть это риск
порчи памяти за неизвестную выгоду.

### Класс «бесполезная работа», измеренный

**3. `dlls/wined3d/adapter_gl.c:3336` — `ARB_DEPTH_CLAMP` промотируется по версии.**


Исправление: добавить `ARB_DEPTH_CLAMP` к снимаемым для GLES.

**4. `dlls/wined3d/ffp_gl.c:889`, `line_antialias()` — вызов вообще без защиты.**

## 6j. Диагноз: фризы игрока — это линковка программ, и патч 27 их не покрывает

Игрок описал явление точно: «пришёл на новую сцену — фриз, увидел новых врагов —
фриз, потом стабилизируется». Это стоимость первого использования, а не случайное
зависание, и она наконец измерена **в геймплее**, а не в демо — благодаря
`harness/autoload_save.sh`, который сам грузит сохранение и потом ходит.

Кольцо пробника за прогон «загрузка сохранения + 12 проходов ходьбы»:

```text
link_program     n=27   сумма 5765.1 ms   макс 299.5 ms   (~214 ms на линковку)
compile_shader   n=31   сумма  140.9 ms
slow_bind        n=34   сумма   55.5 ms
ИТОГО по шейдерам        5961.6 ms

остановки того же прогона: 5180, 3466, 2213, 460, 455 ms  (сумма ~11.8 s)
полосы 50-100/100-200/200-500/>500 ms: 90/8/5/6
```

**Шейдеры объясняют около половины всех остановок: 6.0 s из 11.8 s.** Для сравнения,
в демо было 2.5 s из 8-9 s при всего 12 линковках. Геймплей линкует вдвое больше и
вдвое дороже.

### Почему патч 27 при этом не помогает

`link_separable_stage` — **ноль записей**, все 27 линковок монолитные. Причина в
коде, `dlls/wined3d/glsl_shader.c:11023`:

```c
if (priv->mgs2_separable_enabled && ffp_vs && ffp_ps && !hshader && !dshader && !gshader)
```

Путь требует одновременно FFP-вершинного и FFP-пиксельного шейдера. В геймплее
MGS2 рисует программируемым VS, поэтому `ffp_vs` равен NULL и патч отключает себя
по построению. Это не дефект реализации: раздел «Незакрытое» его собственного
брифа прямо фиксирует, что пары «программируемый VS + FFP PS» намеренно идут
монолитным путём.

Следствие, которое стоит записать без обиняков: **измеренный выигрыш патча 27
(−42%, 116 ms против 201 ms) относится к рации и меню, а не к тем фризам, на
которые жалуется игрок.** Он полезен, но не в этом сценарии.

### Что из этого вытекает как работа

Расширить separable-путь на пары «программируемый VS + FFP PS» — это единственная
известная правка, которая бьёт прямо в измеренные 6 секунд. Её цена названа в том
же разделе брифа: нужна отдельная проверка uniform-локаций для `vs_c[]`, потому
что у stage-программы локации свои, а wined3d их кэширует. Риск реальный: при
разработке патча 27 таких дефектов было найдено шесть, каждый из которых сам по
себе ломал картинку.

Вторая половина остановок (около 6 s из 11.8) шейдерами **не** объясняется и
по-прежнему не названа. Кандидаты после исключений раздела 6f: загрузка ресурсов
на стороне игры и создание текстур.

### Сначала опровержение

Раздел 6j утверждал, что патч 27 в геймплее не срабатывает: 27 линковок, все

## 6l-a. Исходные измерения патча 31 (сохранены как есть)

Пришёл из вопроса игрока: нельзя ли уменьшить слои эмуляции для этих фризов?
Для линковки шейдера — нет, она внутри нативного компилятора Mali, и это записано
замером (`GL_LINK_STATUS` сразу после стоит 5-8 мкс). А вот culler делал настоящую
арифметику в эмулируемом x86 **на каждый проверяемый draw**: 349 раз за кадр, обход
всех вершин диапазона.

Кэш, который там стоял, не попадал никогда (0 из 112 800) и был снят патчем 28.
Перекеить его нельзя по той же причине, по которой он и не попадал: игра
перезаписывает вершинные буферы каждый кадр, и AABB честно меняется. **Поэтому патч
31 не кэширует ответ, а меняет вопрос.**

Каждый буфер держит **одну консервативную коробку** на все байты, которые он
объявил валидными; она строится при первой проверке после записи и переиспользуется
всеми последующими draw до следующей записи. Инвалидация — ровно там, где
инкрементируется `mgs2_geometry_generation`.

Коробка больше точной, поэтому может только **не отбросить** то, что точная
отбросила бы, и никогда не отбросит видимое. Есть откат на точное сканирование,
когда список валидных диапазонов переполнен или когда stride/offset не совпали с
закэшированной парой.

```text
MGS2_D3D8_CULL_BOX=1    48.68 fps   (холодное)
MGS2_D3D8_CULL_BOX=1    48.39 fps   (горячее, 81.7 °C — снимает вопрос о нагреве)
MGS2_D3D8_CULL_BOX=0    27.92 fps   (горячее)
в проде                 48.96 fps
```

**+74%**, снимки обоих плеч неразличимы: тот же коридор, поза, стол, кресло,
клавиатура, монитор, радар. `page fault` ноль, GL-ошибок ноль. Замер сделан на
одинаковом маршруте благодаря `autoload_save.sh`, а не на демо, где потолок 60 fps
всё маскировал.

Порядок плеч специально перевёрнут: ON гонялось и первым на холодном, и потом на
горячем — разница 0.3 fps, тогда как OFF на горячем даёт 27.92. Нагрев в этом
результате не участвует.

Известный предел, не наблюдавшийся: сцена, где валидные диапазоны одного буфера
покрывают почти весь уровень, даст коробку слишком большую, чтобы что-то отбрасывать
— тогда теряется +17.5% самого culler'а, но экономия сканирования остаётся. Отказ в
худшую сторону — медленнее, никогда неверно, и `MGS2_D3D8_CULL_BOX=0` возвращает
прежнее поведение за один прогон.

**Больше не в production, см. 6l.** Файлы на месте: `d3d8_p31_cullbox.dll`,
`wine-patches/31-cull-box-per-write.patch`, применяется с `-F0`. Включается
`MGS2_D3D8_CULL_BOX=1` за один прогон, без пересборки.

## 7. Следующий ограниченный шаг

Прежний план этого раздела предполагал, что patch 27 снят и проверяется плечами.
Он больше не действует: патч в production, а планомерный A/B отвергнут как
непрактичный — игрок не может играть «в ожидании фриза», и это разумно.

Поэтому режим работы теперь **оппортунистический**, а не экспериментальный:

```text
1. играть нормально; при фризе снять freeze_capture.py ДО убийства процесса
   (если рядом нет терминала -- просто перезапустить, потеря лишь одного случая)
2. совпала сигнатура раздела 2 -> дефект живёт в Box86/libmali и не связан
   ни с patch 27, ни с patch 26; тогда следующий шаг -- внутрь box86, а не A/B
   другая сигнатура        -> это новый дефект, разбирать отдельно
3. при наработке двух-трёх захватов появится частота, и только тогда любой A/B
   становится судимым
```

Если к A/B всё же вернутся, первым остаётся плечо 6a, а не patch 27: захваченный
futex висел в арене Box86, и мост memmove — единственный снимаемый элемент,
который туда лезет.

Отдельно: любой будущий прогон patch 27, задуманный как измерение, должен идти
с `MGS2_GPU_PROBE=1`. В production он выключен сознательно, и это правильно, но
именно поэтому фриз 12 августа не дал данных о шейдерах.

При любом следующем фризе снимать **до** убийства процесса:

```sh
python3 harness/freeze_capture.py --out /tmp/freeze-$(date +%Y%m%d-%H%M)
```

Скрипт написан по этому захвату и делает ровно раздел 2 за один проход: два
среза каждого потока, `syscall` с аргументами, слово futex из `/proc/<pid>/mem`,
kernel stacks, sha256 всех смонтированных модулей, память, клок, температуры.
Опроса в цикле в нём нет — правило 2 и предупреждение брифа #28 про
`stall_watch*` соблюдены.

Читать его вывод с оговоркой, которую он печатает сам: ожидание без таймаута на
неизменившемся слове — **норма** для простаивающего воркера, и запаркованный
threadpool на этом уровне неотличим от дедлока. Проверено на sway: его
`mali-utility-wo` выглядят точно так же, как выглядели в игре. Диагноз несут
именно потоки с большим utime, которые обязаны работать, чтобы шёл кадр.

## 8. Мёртвый груз в продовом стеке: `ntdll_fastyield.so`

Найдено при разборе ранних патчей. Продовый лаунчер монтирует
`ntdll_fastyield.so` поверх системного `ntdll.so`, но патч 05 включается только
переменной `MGS2_YIELD`:

```c
const char *s = getenv( "MGS2_YIELD" );
if (s && !strcmp( s, "fast" )) mode = 1;
else if (s && !strcmp( s, "none" )) mode = 2;
else mode = 0;                  /* stock NtYieldExecution */
```

`MGS2_YIELD` в окружении живого процесса отсутствует (проверено на pid 24615),
значит режим стоковый и патч не делает ничего. Патч 05 целиком состоит из этого
переключателя — другого содержания в нём нет.

Итог: мы держим поверх системного `ntdll` собственную пересобранную копию
core-модуля ради выключенной функции. Функциональной пользы ноль, а
риск-поверхность — целый кастомный `ntdll`. Как подозреваемый по фризам он тоже
выпадает: неактивный код их вызывать не может.

Решение: строка монтирования убрана, прод возвращается на системный `ntdll`.
Модуль остаётся в `binaries/`, и одна строка `mount_bind` вернёт его, если
когда-нибудь понадобится измерить `MGS2_YIELD=fast`.

Статус на 2026-08-12: применено в `device/launch-play.sh`, **на устройстве ещё
не развёрнуто и не проверено** — деплой заблокирован недоступностью shell в той
сессии. Проверка после развёртывания, ожидаемое изменение поведения нулевое:

```text
1. в /proc/mounts НЕТ строки для /usr/lib/wine/i386-unix/ntdll.so
2. игра поднимается, кадр есть, звук есть
3. загрузка сохранения проходит  <- сегодня это самый хрупкий путь стека,
                                    проверять обязательно
```

Это единственное удаление за 12 августа. Оно не связано с фризами: неактивный
код их вызывать не может, и как подозреваемый модуль выпал ещё при разборе.
